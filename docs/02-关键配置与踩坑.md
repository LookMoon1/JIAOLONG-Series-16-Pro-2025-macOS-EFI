> 以及哪些做法**已经证伪、不要再试**。

## 一、突破 PCI configuration 卡死（最关键）

### 症状

内核启动后停在下面这一行，之后没有任何输出：

```
pci (build 19:00:35 Jul 31 2026), flags 0xc3080
```

即 `[PCI configuration begin]` 阶段卡死。

### 失败过的尝试

| 尝试 | 结果 |
|---|---|
| `npci=0x2000` | flags 变为 `0xc1080`（XOR = 0x2000，说明参数生效了），**但仍卡住** |
| `npci=0x3000` | flags 变为 `0xc0080`，**仍卡住** |
| BIOS 开 Above 4G Decoding / 关 Resizable BAR | **本机 BIOS 没有这两个选项** |
| 反复改 AMFI / `DisableVariableWrite` | 与 PCI 无关，方向错误 |

1401 源码中处理 PCI 卡点的规则 `bootlog-pci-config` 只有 `0x2000 → 0x3000` 两级，
用尽后官方建议是"BIOS 开 Above 4G"——而本机 BIOS 没有该项。

### 真正的解法

```xml
<key>UEFI</key>
<dict>
    <key>Quirks</key>
    <dict>
        <key>ExitBootServicesDelay</key>
        <integer>3000</integer>   <!-- 关键！ -->
    </dict>
</dict>
<key>Booter</key>
<dict>
    <key>Quirks</key>
    <dict>
        <key>ProtectUefiServices</key>
        <true/>               <!-- 关键！ -->
    </dict>
</dict>
```

依据是**同配置**（9955HX + RTX 5060 Laptop）的
[ASUS TX Gaming 7Pro EFI](https://github.com/VisualTechStudio/ASUS-TX-Gaming-7Pro-Ryzen-CN-OpenCore-EFI)
—— **本项目的 PCI 卡点修复方案来源于该成功案例，并非原创**。
详见 [06-参考文献.md](06-参考文献.md)。

> **注意位置**：`ExitBootServicesDelay` 属于 **`UEFI → Quirks`**，不是 `Booter → Quirks`。
> 放错段位会被 OpenCore 忽略，且日志报 `OCS: No schema for ... at NN index`。

### 附带发现的 NVRAM 陷阱

1401 的 `keep-boot-args` 规则（`p1401/policy.py:414-420`）**绝不覆盖已存在的 boot-args**
——这是为保护已装好的 macOS 不被误改。后果是：

> 如果第一次启动已经把 boot-args 写进主板 NVRAM，之后**改 U 盘的 `config.plist` 完全无效**。

**修复**：必须同时配置 `NVRAM → Delete → boot-args`，让每次启动先删旧值再写新值：

```xml
<key>NVRAM</key>
<dict>
    <key>Delete</key>
    <dict>
        <key>7C436110-AB2A-4BBB-A880-FE41995C9F82</key>
        <array>
            <string>boot-args</string>
        </array>
    </dict>
    ...
</dict>
```

**判断参数是否真的生效**：看 OpenCore 日志里 `AAPL: #[EB|MBA:OUT]` 那一行是否包含你的新参数。

## 二、显卡：NullMoth 驱动

### 依赖的 boot-args（**不能删**）

```
nvfb=1 nvaccel=1 nvfbheads=4 -nvkmsnosmooth gfxrst=4
amfi_get_out_of_my_way=0x1 amfi=0x80
```

- `amfi=0x80` 与 `amfi_get_out_of_my_way=0x1` 是 **NullMoth 驱动的硬依赖**，
  改了或删了驱动加载不起来；
- `csr-active-config = 0x0A43` 同理。

### 必须 Block 的 kext

```xml
<key>Kernel</key>
<dict>
    <key>Block</key>
    <array>
        <dict>
            <key>Identifier</key><string>com.apple.iokit.IONDRVSupport</string>
            <key>Enabled</key><true/>
        </dict>
    </array>
</dict>
```

**原因**：`IONDRVFramebuffer` 是 Apple 的 boot framebuffer，会**抢走 NVRMFB 的显示索引 0**，
导致 NullMoth 驱动无法接管内屏。

### 核显处理

Radeon 610M `1002:13C0` 在 macOS 无驱动，构建期已用 `disable-gpu` 关闭。
它在 PCI 总线上可见，会干扰设备枚举，**保持禁用**。

## 三、Wi-Fi：MT7922 + YYavicWiFi

### 背景

MediaTek MT7922（AMD 称 RZ616）长期没有 macOS 驱动。
[YYavicWiFi](https://github.com/yusufcanyavic/YYavicWiFi) 是第一个让它以**原生 macOS Wi-Fi 栈**
（IO80211 / Skywalk / airportd）工作的开源驱动。

### 本机的特殊之处：build 门槛

YYavicWiFi 0.8.0 的 macOS 26 原生层是针对 **26.7.2 (25G332)** 编译的，
而本机系统是 **26.7.3 (25G342)** —— **差一个 build**。

kext 在启动时会检查 build 版本，不匹配就自己禁用：

```
YYavicWiFi: native Wi-Fi layer disabled, unsupported macOS
```

**解法**：boot-args 加 `-yyavicnoverify` 跳过该检查。

已验证：**25G332 → 25G342 的 IO80211 布局一致**，所以跳过检查后能正常工作。

> ⚠️ 上游把这个开关标为 **testers-only**，因为"布局不对会 panic"。
> 本机实测可用，但这属于**依赖运气**的配置。
> **系统更新前请先备份 EFI**，并检查是否有对应新 build 的 kext 版本。

### 国家码

```
yyavic-cc=CN
```

决定可用信道。CN 地区：2.4 GHz 1–13，5 GHz 36–64 / 149–165。
不设置则只用各地区通用信道（2.4 GHz 1–11，5 GHz 36–64）。

### 验证方法

```bash
# 1. 驱动是否生效
log show --last 3m | grep -i yyavic

# 2. 硬件是否认到
system_profiler SPAirPortDataType

# 3. 接口是否存在
networksetup -listallhardwareports
```

**成功标志**（本机实测输出，MAC 已隐去）：

```
Interfaces:
    en1:
      Card Type: Third-Party Wireless Card
      Firmware Version: YYavicWiFi 0.8.0 (MT7922)
      MAC Address: <你的网卡MAC>
      Country Code: CN
      Supported PHY Modes: 802.11 a/b/g/n/ac
      Status: Not Associated
      Local Wi-Fi Networks: ...（能扫到网络即成功）
```

> 注意 `en1` 是**你的机器上**的接口名，不同机器可能是 `en0` / `en2`。
> 关键看 `Firmware Version` 是否显示 `YYavicWiFi 0.8.0 (MT7922)`。

**失败标志**：日志出现 `native Wi-Fi layer disabled, unsupported macOS` → 检查 `-yyavicnoverify` 是否生效。

### 已读到的教训

- **NVRAM 守卫可能失效**：README 说有 `yyavic-arm-guard` NVRAM 守卫，
  在 native layer 启动失败后下次自动跳过。但本机 `DisableVariableWrite=True`
  会让 **NVRAM 写入静默失败**，所以此守卫大概率不生效 → 回滚只能靠 Windows 下改 `config.plist`。
- **安全档**：`-yyavicoff` 可让驱动只跑 radio、不启动 native layer，用于验证 kext 本身不炸。
- **限制**：不支持 WPA3-only、802.1X/Enterprise（eduroam）、6 GHz、AirDrop/AWDL、个人热点 AP。
- **"Private Wi-Fi address" 必须保持开启**（Fixed 或 Rotating），关掉会因全零 MAC 无法加入网络。

## 四、亮度：`nvrmacpibl=1`

NullMoth 驱动的背光路径是**opt-in** 的：

```c
// Opt-in (boot-arg nvrmacpibl=1)
on = (PE_parse_boot_argn("nvrmacpibl", &v, sizeof(v)) && v) ? 1 : 0;
```

**机理**：驱动通过固件的 NBCI `_DSM`（`GETOBJBYTYPE 0x10`、`GETBACKLIGHT 0x14`）和 `_DOD`
读取背光。没有这些 ACPI 对象时，`NV0073_CTRL_CMD_SPECIFIC_GET_BACKLIGHT_BRIGHTNESS`
返回 `NV_ERR_NOT_SUPPORTED`，NVKMS 就不会调用 `nvkms_register_backlight()`。

**本机结果**：加 `nvrmacpibl=1` 后**亮度滑块可用**（控制中心可拖动调节）。

> ⚠️ **但 Fn 键无效，且组合使用会导致系统重启 —— 见下方专项警告。**

> 上游默认关闭是因为这些 ACPI 调用曾在少数机器上挂起。**若加了这个参数开机卡死，先删它再排查。**

## 四之二、⚠️ 已知严重问题：Fn 键会导致系统重启

> **状态：未修复（截至 2026-11 仍在调查）。此问题已实测复现，请勿当成配置错误反复折腾。**

### 现象

| 操作 | 结果 |
|---|---|
| 单独按 **Fn** 键 | ❌ **无任何反应**（不触发任何功能） |
| **Fn + F 功能区按键**（如 Fn+F1/F2/F3…） | 🔴 **系统直接重启** |
| 单独按 F1–F12 功能区按键 | 正常（作为普通功能键使用） |

> 注意：重启不是内核 panic 日志里的那种 panic，而是**整机直接复位**。

### 已确认的事实

1. **`BrightnessKeys.kext` 已加载**，但它只在 `Fn+亮度键` 被正确识别时才起作用；
   本机的 Fn 键本身没有产生 macOS 可识别的 key event，所以它无从生效。
2. **亮度滑块本身是正常的**（`nvrmacpibl=1` 生效），说明背光链路通，问题**不在亮度驱动**，
   而在**键盘扫描码 / EC 层**。
3. 键盘是 **PS/2**，走 `VoodooPS2Controller` 的 `VoodooPS2Keyboard`。
   其内置映射表里已经定义了 `Fn+f1..f12` 的宏（见 kext 的 `Info.plist`），
   但那是**针对其它机型的 EC 行为**写的，与本机 EC 不符。

### 可能原因（尚未验证）

- Fn 组合键在本机会触发 **EC query**，而该 query 在 macOS 下的处理路径与 BIOS/Windows 不同，
  可能引发 AC 断电复位（S5 边界情况）。
- `SSDT-EC` 隐藏了真实 EC，Fn 组合键的 query 可能落空后触发异常。
- 或与 `JiaoLongEC.kext`（蛟龙专用 EC 补丁）的知识库有关。

### 给其他用户和 AI agent 的建议

- ✅ **日常使用请避开 Fn 组合键**；需要亮度就用菜单栏/控制中心滑块。
- ❌ **不要**为了修 Fn 键去删 `BrightnessKeys.kext` —— 它没有害处，删了亮度滑块也不会好。
- ❌ **不要**在没有备份的情况下尝试改 `SSDT-EC` / `JiaoLongEC` 的 EC query 映射。
- 🔍 若要排查，先在 macOS 里看 Fn 按下时有没有产生事件：

  ```bash
  # 终端里按 Fn / Fn+F1，看是否有输出
  ioreg -l | grep -i "AppleEmbeddedKeyboard\|PS2Keyboard"
  log show --last 2m | grep -iE "ps2|fn key|brightness"
  ```

- 🧷 排查前**先备份 EFI**，并准备好暴力断电之外的恢复路径（本机配置全在 U 盘上，可在 Windows 下改回）。

> 这是本 EFI **已知的、未解决的功能缺陷**。它不影响日常使用（只要不按 Fn），
> 但足以让人误以为自己装错了 —— 所以在此明确记录。

排查命令：

```bash
log show --last 1m | grep -i backlight
# 期望看到：NVRM-xnu: backlight registered
# 若看到：internal panel, but NVKMS registered no backlight → ACPI 侧缺件
```

## 五、触控板与键盘

- **键盘是 PS/2**（`MSFT0001`，i8042），macOS 没有内建 PS/2 驱动 → `VoodooPS2Controller` + 其 PlugIns。
- **触控板是 I2C HID**（`UNIW0001` / `093A:0255`）→ `VoodooI2C` + `VoodooI2CHID`。
- 本机 GPIO 中断不需要额外 SSDT，用 **`-vi2c-force-polling`** 轮询即可。
- `VoodooPS2Controller` 自带的 `VoodooInput.kext` 与 `VoodooI2C` 的会产生冲突，
  **只能启用一个 provider**（本 config 中已按正确顺序处理）。
- ⚠️ **Fn 键不可用且组合键会重启**，见第四节之二。`VoodooPS2Keyboard` 内的 Fn 映射表
  是针对其它机型的 EC 行为写的，与本机不符。

## 六、声卡：为什么没有声音

> **状态：未尝试修复。** 以下为**分析推断**，尚未经过实机验证 —— 请勿当成已确认结论。

Conexant/Senary **SN6140，vendor `0x14F1` / codec `0x1F87`**。

官方 AppleALC 1.9.9 的 Conexant codec 表里有：

```
0x14f11f72 (CX8050)  0x14f11f86 (CX8070/CX11880)  0x14f11fd6 (CX8150)
0x14f12008 (CX8200)  0x14f120d0 (CX8400)          0x14f150xx (CX20561…CX20757)
```

**`0x14f11f87` 不在其中** —— 与 CX8070 只差最后一个 nibble。

> **重要**：AppleALC 是 **AppleHDA 的补丁/插件**。
> macOS 26 是否仍存在可用的 AppleHDA 宿主，直接决定这条路线是否可行。
> **在动手买/装 AppleALC 前，请先在系统里确认**：
> ```bash
> ls /Library/Extensions/NMXAudio.kext          # NullMoth 3.0 自带的 macOS 26 HDA 驱动
> kextstat | grep -i nullmoth
> ```
> - 若 **NMXAudio 存在** → 问题在它对 SN6140 的 codec 适配，方向完全不同；
> - 若 **不存在** → 先更新 NullMoth 驱动包，再谈 AppleALC。

社区方案（macOS 15 上已验证，**macOS 26 上未有验证记录**）：
[chenhggu6475/Senary-SN6140-AppleALC-Hackintosh](https://github.com/chenhggu6475/Senary-SN6140-AppleALC-Hackintosh)，
layout 15，boot-args 加 `alcid=15 alcdelay=1000`。
（`alcid=` 在 AppleALC 内部优先级最高，会覆盖任何 `layout-id` 属性。）

**最省心的替代：USB 声卡（免驱，20–40 元）。**

## 七、已证伪清单（**不要再走回头路**）

| 做法 | 为什么错 |
|---|---|
| `npci=0x2000` / `npci=0x3000` | 试过且确认参数生效，只改变 flags 数值，不解卡点 |
| 改 AMFI / `DisableVariableWrite` 去修"安装器损坏" | 参数确实生效了，但照样报错；真因是载荷放错 |
| 拿裸 `SharedSupport.dmg` 当离线安装载荷 | 永远报 `pkgdmg is missing a footer`，必须放**整个 `.pkg`** |
| Recovery 里 `kmutil create` 重建内核集合 | 跨卷缺系统 KC 上下文，必然失败；驱动要在系统内跑 `install.sh` |
| 用二进制 plist 写 config | ocvalidate 报 `Couldn't parse serialized file`，**必须 XML** |
| `-x` 安全模式 | 实测内核起不来 |
| 给内屏做 HiDPI 自定义分辨率 | 驱动拒绝自定义 framebuffer；只有 1280×800（2×）真清晰 |
| 内置 MT7922 蓝牙传输层 | 曾认为"macOS 没有对应驱动"，**实际用 BlueToolFixup + SimpleMtkBtFw 可正确配对连接**（但可用性未验证） |
| 移除 `SSDT-EC` 想恢复电池百分比 | 会让 AppleACPIEC 卡死，启动无法完成 |
| `ResizeAppleGpuBars = 12`（以为代表 4 GiB） | 该值是 PCI 规范代码，`12` = **4 KiB**，会直接禁止符/瞬断 |
| `Booter>Quirks>ResizeGpuBars` | 位置错误，应属 `UEFI>Quirks`；放错会被忽略 |
| 用其他 OpenCore release 覆盖现有 EFI | 本机已是 DBG-109（1.0.9 dev），**比官方 1.0.8 新**，覆盖是倒退 |

## 八、离线安装器的坑（历史记录，仍有参考价值）

安装阶段曾被"安装无法继续，因为安装器已损坏"（**Code=255**）卡住很久。
真因**不是签名、不是 AMFI、不是磁盘权限**，而是：

> Apple 的 `osinstallersetupd` 要读 **pkg 文件最后 1024 字节的 UDIF `koly` 尾部**，
> 用其中的 `dataForkOffset` 定位 dmg 在 pkg 内部的起点。

| | `dataForkOffset` | `dataForkLength` |
|---|---|---|
| 独立 `SharedSupport.dmg` | **0** | 18,370,913,792 |
| `InstallAssistant.pkg` 尾部 | **17,949,425** | 18,370,913,792 |

两者 `dataForkLength` 完全一样，**只差那个偏移** —— 而只有 pkg 才有。
裸 dmg 拿不出来 → `pkgdmg is missing a footer` → 校验失败 → 报 Code=255。

**正确做法**：把整个 `InstallAssistant.pkg` 改名为 `SharedSupport.dmg` 使用。
Apple 官方 postinstall 本来就是这么链接的：

```bash
/bin/ln -fFh "${PACKAGE_PATH}" "${SHARED_SUPPORT_PATH}/SharedSupport.dmg"
```

## 九、红线

1. **macOS 之外的任何分区一律不动**。任何抹盘/分区操作前，现场确认目标分区是 **APFS** 的 macOS 分区
   （用 `diskutil list` / `Get-Partition`，**不要靠容量猜**）。
2. 改 `config.plist` 前先备份，命名沿用 `config.plist.<备注>-<时间戳>`。
3. 改完必须跑 `ocvalidate`，结果必须是 **`No issues found`**。
4. 所有配置改动落在 **U 盘的 `EFI/OC/config.plist`**（OpenCore 在 U 盘上），
   好处是出问题可以在 Windows 下直接改回来，不用进 Recovery。
5. **不要用 1401 的 `cleanup-injected.sh`**：它是为"注入失败"准备的，
   而正常运行时驱动是生效的，照它删文件可能把显卡搞黑。
